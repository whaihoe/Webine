# Historical Cloudflare proxy-to-Vercel security reference

> **Historical only.** These controls describe Cloudflare acting as a proxy in front of the former Vercel deployment. They do not configure the live Worker, R2 or static-hosting platform. Use [the Cloudflare cutover runbook](../cloudflare-cutover-runbook.md) for current operations.

Apply these steps to the Webine zone only after reviewing current traffic. Cloudflare protection applies only to requests passing through proxied DNS records.

1. In **DNS > Records**, confirm `madebywebine.com` and `www` are orange-cloud proxied. Leave mail, verification and other non-HTTP records DNS-only. Verify both website hostnames still reach the Vercel deployment. Roll back by returning only the affected website record to DNS-only.
2. In **SSL/TLS**, use **Full (strict)**, enable **Always Use HTTPS**, set minimum TLS to 1.2 and retain TLS 1.3. Introduce HSTS cautiously after HTTPS works on every required subdomain. Start without `includeSubDomains` or preload if any subdomain is uncertain. Roll back HSTS before changing HTTPS availability, noting that browsers retain it until expiry.
3. In **Turnstile**, create a Managed widget named `Webine Contact Production` for `madebywebine.com` and `www.madebywebine.com`. Enter the site key and secret through Vercel's secure environment-variable UI as `VITE_TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY`. Do not store the secret in Git. Verify one Preview submission before Production.
4. Create an enquiry rate-limit rule matching `http.request.method eq "POST" and http.request.uri.path eq "/api/enquiries"`. Start at 10 requests per 60 seconds per IP with Managed Challenge or Block and a 10-minute mitigation when the plan supports it. Verify normal form submission, then monitor false positives. Disable this rule to roll back.
5. Create an Admin rate-limit rule matching `http.request.uri.path eq "/api/admin" or starts_with(http.request.uri.path, "/api/admin/")`. Start at 120 requests per 60 seconds per IP. This is higher because one Admin page can make several authenticated requests. Verify sign-in, dashboard, editing and upload before retaining it.
6. Create a public CMS rule for GET or HEAD requests to `/api/projects`, `/api/projects/*`, `/api/site-settings` and `/sitemap.xml`. Start at 300 requests per 60 seconds per IP, then tune from Security Events. This reduces slug scanning and cache-busting without treating ordinary crawling as hostile.
7. Create method rules that block non-POST requests to `/api/enquiries` and methods other than GET or HEAD on public read-only endpoints. Test one rejected method and normal browsing. Disable only the affected rule if an integration uses an unexpected method.
8. Enable available managed WAF rules conservatively. Begin in log or low-sensitivity mode where offered, review Security Events and raise enforcement only after false positives are understood.
9. Review Bot Fight Mode rather than enabling it blindly. It may affect Clerk, Turnstile, Googlebot, monitoring and legitimate automation, while Free-plan controls may be coarse. Test all these flows and turn it off if verified traffic is challenged incorrectly.
10. Add cache bypasses for `/admin*`, `/preview*`, `/api/admin*` and `/api/enquiries`. Do not create a broad Cache Everything rule for `/api/*`. Vercel Function cache headers remain the initial authority for public CMS responses.
11. In **Security > Events**, save filters for enquiries, Admin, projects and site settings. Review repeated query variants, scanners, distributed spam, verified Googlebot and false positives during the first week. Record rule changes and rollback decisions.
