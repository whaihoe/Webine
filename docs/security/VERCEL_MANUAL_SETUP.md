# Historical Vercel security and rollback reference

> **Historical only.** This document preserves the prior Vercel security state for an approved rollback during the Cloudflare observation period. It is not a live setup guide. Use [the Cloudflare migration plan](../cloudflare-migration-plan.md) and [the cutover runbook](../cloudflare-cutover-runbook.md) for current operations.

Only use these dashboard steps when the installed CLI or official API cannot apply and verify the setting safely. Names and plan availability can change, so confirm the current project and plan before saving.

1. Open the Webine project and confirm the Production domains are `madebywebine.com` and `www.madebywebine.com`. Check that Production `VITE_SITE_URL` is `https://www.madebywebine.com`. A wrong value affects canonical metadata and sitemap URLs. Restore the previous value and redeploy to roll back.
2. Branch-scoped Preview values are configured for `security/vercel-abuse-hardening`: official Cloudflare Turnstile test credentials, the canonical site URL, the stable Preview hostname and the Clerk authorised party. Production values were not changed. For another branch, add equivalent branch-scoped test values securely and never copy credential values into logs, source or documentation. Remove only that branch's Preview-scoped values to roll back.
3. Vercel Authentication is active and verified for Preview deployments. Keep the public Production custom domain unprotected. Anonymous checks should redirect to Vercel sign-in. Disable Preview protection only if a required external Preview integration cannot support it and the exposure has been reviewed.
4. In **Firewall**, retain and monitor the applied `enquiries-abuse` rule before adding more. It covers exact `POST /api/enquiries`, 10 requests per 60 seconds per IP, and denies excess traffic. The current plan exposed limited firewall capabilities. If the plan later supports more rules, add the Admin, public-read and unsupported-method rules from the Cloudflare checklist one at a time, verify each draft and record its ID. Do not replace the enquiry rule without an equivalent Cloudflare control.
5. In **Usage and Billing**, review Spend Management, usage alerts, billing recipients and any production pause threshold available on the account. Do not enable a pause threshold without accepting the possible website downtime and lost enquiries. Test alerts without deliberately generating high traffic.
6. In **Logs and Monitoring**, save views for `/api/enquiries`, `/api/admin`, public CMS routes, Function errors and CSP report-only messages visible in the browser or log pipeline. Watch Function invocations and duration, Fast Data Transfer, Turso activity, Blob transfer and notification failures.
7. Observe traffic to the exact fixed alias `webine.vercel.app` after production code and metadata stop referencing it. Do not block every `*.vercel.app` hostname. If the exact alias is unused and a supported hostname rule is available, introduce it in log-only mode first and document the later deny and rollback actions.
8. Keep Attack Mode disabled during normal operation. During a verified attack, CLI 58.4.4 supports `vercel firewall attack-mode enable --duration 1h --project webine --scope webine` and early rollback with `vercel firewall attack-mode disable --yes --project webine --scope webine`. It takes effect immediately, so check the current help and use it only for a real incident.

9. The project reports Node.js 24.x, but the hardening Preview build used the repository's Node 22.x engine pin successfully. The dashboard can be aligned to Node 22.x later for clarity, but this is not required for the Preview and should not be changed in Production without a separate verified build.

Every saved change must record the project, rule or setting ID, previous and new state, verification result, rollback action and whether rollback reduces security, affects availability or changes enquiry delivery.
